VitalSense Audit Report
Executive Summary
VitalSense is an early-stage healthcare monitoring prototype for real-time sepsis risk prediction and ICU patient monitoring. It combines:

Frontend: Next.js 16 + React + Tailwind
Backend: FastAPI + WebSockets
ML: XGBoost + LSTM ensemble with SHAP explainability
Simulator: Python EMR/vitals generator
Strengths:

Clean UI/UX direction and strong component layout
Real-time WebSocket design for live prediction streaming
Intentional ML architecture with ensemble and explainability
Docker Compose scaffolding for local full-stack development
Primary weaknesses:

No real authentication/authorization
Backend persists only to in-memory stores
PostgreSQL is declared but unused
ML model artifacts are not committed
No CI/CD, monitoring, or enterprise security controls

Phase 2: Architecture Audit
Frontend architecture
app uses Next.js app router
pages include /, /dashboard, /dashboard/alerts, /dashboard/patients, /dashboard/settings
components are reusable and styled with Tailwind
good separation between page layout and shared components
Issues:

login page is UI-only and redirects client-side without auth state
no global auth/session handling
some dashboard components render placeholder content rather than live data
no explicit mobile/responsive verification beyond Tailwind classes
Backend architecture
main.py starts FastAPI with CORS allow_origins=["*"]
routers: patients.py, alerts.py, predictions.py
manager.py is simple and functional
Critical issues:

database.py exists but is unused
patient and alert data are stored in-memory (patients_db, alerts_db)
backend does not persist to PostgreSQL despite docker-compose.yml
predict tries dynamic ML import, then falls back to heuristic logic if model fails
no OpenAPI security definitions, no JWT, no RBAC
ML architecture
predict.py loads xgb_model.pkl and lstm_model.pt from saved_models
ensemble: 60% XGBoost + 40% LSTM
SHAP explainability via shap_explainer.explain_instance
training assets exist in train_xgboost.py, lstm_model.py
Issues:

saved_models contains docs only, not model artifact files
backend fallback heuristic is used when models fail
no robust model registry or reproducible model versioning in runtime
no inference monitoring, drift detection, or shadow mode
Database design
Docker Compose includes PostgreSQL
code uses only in-memory dicts
no SQL models, ORM, or migrations
patient history is stored in patient_history_db memory only
Impact:

state is lost on restart
not compliant with clinical audit/history expectations
no long-term data storage for reporting or analytics
API design
/patients
/patients/{patient_id}
/patients/{patient_id}/history
/alerts
/alerts/{alert_id}/dismiss
/predict
/ws
Issues:

/patients returns synthetic snapshot-only data
/alerts lacks create/update workflow for clinical triage
/predict mixes prediction, history update, alert generation, and state mutation
no versioned API or documented contract beyond docs
Authentication & RBAC
none implemented
login is purely client-side UI in login-page.tsx
no user roles, no permissions, no session persistence
Deployment setup
docker-compose.yml defines backend, frontend, db
backend .env file expected but not supplied
frontend env values are hard-coded in the compose file
no GitHub Actions / CI
no staging/production configuration
Monitoring & logging
none found
backend uses print() in ML loading errors
frontend lacks logging/error tracking
no metrics, no health endpoint beyond /health
